SSE → turn classify (rules first, Jev stage 2 off by default → fast or full path) → prompt build (memory summary + profile ctx) → fit to 6.7k est. tokens → OpenLux → Groq (gpt-oss-120b → qwen3.8-27b) → OpenRouter tool loop (≤6) → persist → fire-and-forget memory extraction + classification row.

Prompt compositionbuild_system_prompt(memory_summary=…) = SYSTEM_PROMPT (rules 1–22) + AGENT MEMORY block (from memory.md) + CURRENT PROFILE CONTEXT (incl. today's date, rule 19). Rule 7 → get_peer_advice, rule 11 → recall_memory, rule 12 → remember, rules 13–15 → user-requested handles, no un-run action claims, honest get_peer_advice labeling, rules 17–20 → coverage line per named handle + source_handles evidence rule + no invented specifics + state the deliverable's owner, rule 21 → free-first ambiguity (offer a credits/llm tool, never spend silently), rule 22 → tool-call reason discipline + answer from the TOOLS USED note instead of re-running tools. Turn classification → path → tier (PROMPT 5)classify_turn runs rules first and only calls Jev when nothing matched (stage 2 default off — turn_class_jev_enabled, 0.85/0.6, 800 ms). The class picks the tool allowlist (CLASS_ALLOWED: chitchat/history_meta → no tools, memory → free + memory, read_cheap → free only, live_scan → free+credits+llm, write → free+write) and the effort (low for the free-tier classes). Fast path additionally requires no pending-write resolution and no coverage-guarded ask; path_taken records what actually ran. Each turn writes one turn_classifications row after the reply (fire-and-forget — a failed write never breaks a turn) carrying timings; /health merges p50/p95 over the newest 100 turns and omits the block when nothing is measurable.
Tool loop invariantsUSER row persisted before the loop; TOOL rows never re-enter context next request; tool exceptions, malformed JSON arguments, and missing required arguments are caught and fed back to the model as {"error": …} tool messages — the turn always completes (registry validates arguments before dispatch). Every tool runs under a 120 s timeout; a zero-tool reply that claims scan-style work gets one corrective nudge, then an appended honesty disclaimer (see section 6).
Request-fit before every completionThe assembled payload (system + history + current ask + tool specs) is estimated (chars ÷ 3.5) and trimmed to MAX_REQUEST_TOKENS = 6_700 before each call — ladder: drop oldest history → shrink older tool-group results to 1,200 chars → drop the oldest whole tool-group; never the system prompt, the current ask, or the newest tool group (whole-group deletion can't orphan tool_calls). Re-run every loop iteration (tool results grow the transcript); trims are in-memory — the DB keeps full text, each tool result's context copy is capped at 4,000 chars. Still-over sends with a warning: the Groq chain's second model (~8k-token wall) is the backstop, so a qwen 413/429 no longer kills the turn (smoke: context budget: dropped 8 oldest history message(s)…, no 413).
Memory never blocks the replyExtraction runs as a held fire-and-forget task after success; LLM failure → nothing written, Chroma failure → summary-only. remember dedupes exact matches.
Content routing — authentic originals vs activityAll routing lives in services/ingest.py (shared by every own-post path). classify_post_item uses API structural flags when present (Xpoz user-live → kind_source="api") else the text heuristics of classify_post_kind (kind_source="heuristic"): originals (incl. quotes) → posts; @-openers → user_activity reply (user's own words → get_user_activity + voice reply_style); RT-openers → user_activity retweet (shared content, never attributed to the user). The DB expands on every search: every live pull persists all returned handles — picture, display name, follower count — into handle_mappings (origin: live | cache | selected | niche), not just the one the user picks.   • Instant first paint (0 credits): the browser keeps a snapshot of every saved handle (GET /api/handles/saved = local db ∪ remembered, deduped, followers first), loaded at page load and refreshed after each search/selection — each keystroke prefix-filters it in-browser (0 ms, no request), so known handles appear while the 300 ms-debounced full search refines the same dropdown. A db miss shows a breathing skeleton (a gentle in/out pulse — never a false "no matches"), and behind db-served rows a small breathing dot signals the refinement in flight.
  • Context words: the up-to-3 words typed before the @ travel as context and re-rank merged results (exact → local-db lead → context boost → followers desc, within each group) — never sent to Xpoz, ordering only. The list is a half-and-half mix by where each handle came from on this search: about half the slots go to the saved half — everything served from memory (local db / remembered / past-search cache), with local-db handles leading it — and half to the live half, what a fresh Xpoz pull just returned; a side short of half hands its leftover slots to the other so the list still fills to ten. The exact handle you typed stays at the very top, so a known handle like @AtehOfficial is always visible beside fresh results instead of sinking behind higher-follower strangers, and a memory-served handle can never crowd a fresh-pull one out — they sit in different halves.
